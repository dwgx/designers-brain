> 本リポジトリを運用するためのハードルール——人間にも AI にも適用されます。ルールが *must* と定めている場合、違反は `ops/OPS-LOG.md` に記録すべきインシデントとなります。

## 1. 基本原則

1. **パスごとに書き手は 1 人。** どのファイルにも、同時点で書き手はちょうど 1 人だけです（人間、エージェント、またはメインブレイン）。並行する書き手は明示的なハンドオフで調整し、両者が同時に編集することはありません。
2. **すべての主張にエビデンス等級。** `[自述]` / `[史料]` / `[研究]` / `[归纳]` / `[推测]`（本人の証言 / 史料 / 研究文献 / 帰納 / 推測。識別子は原文のまま）。引用には出典が必須です。見つからない場合は「未找到（已查: …）」と書き、空白を黙って埋めてはなりません。
3. **チェックのない主張は認めない。** 実験やスクリプトで実行されるまで、能力は `[UNVERIFIED]` です。「完了」には実行可能な検証（第三者が再実行できるコマンドまたはファイル）が必要です。
4. **状態の権威。** `ops/GOALS.md` が作業状態についての唯一の情報源です。`ops/OPS-LOG.md` は追記専用の履歴です。ディスパッチボードはスナップショットであり、ボードとディスクが食い違う場合は**ディスクが優先**です——その旨を述べてボードを修正します。
5. **ポインタであり、コピーではない。** スキルとインデックスはナレッジファイルを参照します。コンテンツを複製することはありません。コンテンツの実体は常に 1 か所だけに存在します。

## 2. エージェント運用プロトコル

- **ブリーフ形式**（委任作業）：`# Target`（対象ファイル） · `# Change`（手順） · `# Acceptance`（観察可能・検証可能） · 規律の注記。1 ブリーフにつき書き手 1 人。
- **レシート形式**：各作業項目はレシートで締めます——変更点、成果物パス、生の検証出力、4 部構成の自己レビュー（早期アウトプット / 反論 / 機械検証 / サマリ）。完了ステータスはレシートに書きます。ゴールを書き換えてはなりません。
- **禁止される書き込み**（ブリーフで明示的に許可されない限り）：`ops/GOALS.md`、`ops/OPS-LOG.md`、マシンレベルのボード、リポジトリ外のすべて。
- **予算**：ブリーフごとのソフトなツール呼び出し予算。上限に達したら、現時点の最善の状態を着地させ、ギャップを列挙します。決して空回りしません。
- **2 つの障害対応パターン**（実証済み）：
  - *ゼロ出力タイムアウト*（例：チャネルがタイムアウトして成果物なし） → 別のチャネルで再ディスパッチし、より小さく分割します。
  - *実行途中のクラッシュ（部分的な成果物あり）* → **同じセッションを再開**します。まず着地済みのものを検証し、確認せずに白紙から再開してはなりません。

## 3. リサーチプロトコル

- 一次資料（作品、書簡、論考、美術館の記録、アーカイブ）を優先します。ドシエ（資料ファイル）の各節は等級を明記します。
- 引用：逐語で、出典付き（書名 / 書簡 / URL + 判明している場合は日付）。引用の機械翻訳は翻訳であることを明記してください。
- **操作可能なルール**（「実行できるもの」）を蒸留し、内面状態は扱いません。原則はエビデンスからの帰納であり、画家の心についての主張ではありません。
- 新しいドメインは登録契約（`docs/ARCHITECTURE.md` §3.2）に従います：カード + インデックス + コンフリクト + 出力マッピング + 強度 + エビデンスが揃ってから `status: active` とします。

## 4. 検証プロトコル

- すべての実験には検証スクリプトを同梱します。受け入れ条件 = 検証スクリプトがパスし、生の出力をレシートに貼付することです。
- **独立レビュー**：成果物は、それを生み出していないエージェントが*クリーンなコンテキスト*（プロセスの語りは持ち込まず、成果物 + ルーブリックのみ）でレビューします。レビューは水増ししてはならず、「検証できない」も有効な判定です。
- **決定論コントラクト**（アニメーション / コード出力）：`templates/determinism_contract.md` の C1–C10。**順序を変えた再レンダーチェック**を含みます——連続した再レンダーは状態バグを隠し得るため、常に非連続のサンプルを再レンダーし、フレームハッシュを比較してください。
- Blender 出力：ビット完全一致が実証されない限り、正直に言える上限は P1 決定論の注記（EEVEE サンプリングノイズの範囲内）です。
- 三者同期ルール：蒸留された事実が変わったら、まず唯一の情報源を更新し、次にそれを引用する派生成果物（例：コンフリクト一覧 → スタイルカード → 実験設計）を更新します。

## 5. コンポジションとコンフリクトのプロトコル

- 2 つのモジュールのコンポジション（組み合わせ）には、順序どおりの完全なプリチェックが必要です：コンフリクト表のスキャン → ニアミスの明示値 → N1 反制約の再計算 → N3 軸所有権（補助的なコンフリクト行は**完全に削除**し、決して降格させません） → N4 分割の判断（同一の画素統計 → 一方を選ぶ。分離可能な領域 → ゾーニング表 + マスク） → N9 受け入れ（メインモジュールのフルセット + 補助の非コンフリクト軸。「コンフリクト軸における二重基準」は失敗です）。
- 黙った妥協は禁止です：すべてのマージは、一方を保つか、面をゾーニングするか、コンフリクトする条項を文書化された句式で書き換えるかのいずれかでなければなりません。
- 権威ファイル：`knowledge/cross/conflicts.md`（C-01–C-18、N1–N9）。

## 6. 画像チャネルのプロトコル

- チャネル：ゲートウェイ直結 API。**素のモデル名** `grok-imagine-image-2.0`（このパスでは `buddyfarm/` プレフィックスを付けると 404 になります——CLI とは逆）。要求は 1024×1536、実際の返却は 768×1152。
- このチャネルには**ネガティブプロンプトのパラメータがありません**：ネガティブ部分はリクエスト記録にアーカイブされますが、送信されることはありません。
- アーカイブ契約：`req` / `resp` / 画像 + `sha256` マニフェスト。追跡可能ですが再現可能ではありません（シードなし）——再現性を約束しないでください。
- 詳細とプローブのエビデンス：`knowledge/cross/image_channel.md`。

## 7. スキル対話プロトコル

- 設計リクエストに対するスキルの最初のアクションは、**初回質問パッケージ（first-ask package）**です（3+2 項目。デフォルトは口頭で明示。≤3 ラウンド）。オプトアウト（「とにかくやって」）は許可されますが、一行の前提リストとともに記録する必要があります。
- 視覚的な決定には**目に見える**候補（2〜3 件）が必要で、提示後は必ず停止します。`design-brief.md` ゲートファイルに、意図 / 非目標 / 制約 / ユーザーの逐語の選択 / 前提 / 承認範囲を記録します。承認は、実際に提示されたものだけを対象とします。
- 全文プロトコル：`skills/designers-brain/SKILL.md`。根拠：`docs/skill/skill_spec.md`。

## 8. Git とリリースのプロトコル

- コミットメッセージ：英語、命令形、AI の帰属表示なし。`commit` は自由です。**push には 3 つのチェック**を返信に貼付することが必要です：(1) **パスレベルのクリーン**——`git status --porcelain <自分の書き込みパス>` が空であり、ツリー全体の `git status --porcelain` には**宣言済み**の他者のパスだけが現れ、返信で 1 件ずつ列挙すること（並行作業では「ツリー全体がクリーン」は決して成立しない——これは ModuleCards42 の push 拒否事案に対するプロセス修正（待复核））；(2) ローカルのログが意図と一致、(3) diff の統計に無関係なファイルがない。
- コミット禁止：シークレット、認証情報、サードパーティのメディア（`.gitignore` 参照）、マシン固有のキャッシュ。公開前にシークレットスキャンを実行してください。
- レイアウト変更は `docs/MIGRATION.md`（旧 → 新パス表）に記録します——履歴は `git mv` で保存します。

## 9. i18n プロトコル

- `docs/` とルートの README 3 言語版は、英語が正本です。`docs/i18n/zh-CN/` と `docs/i18n/ja/` は翻訳であり、英語原本が実質的に変更されたときに更新します（または明示的に stale としてマークします）。
- 製品名、ファイルパス、プロトコルのキーワード（N1–N9、C-01–C-18、エビデンス等級）は翻訳しません。翻訳するのは文章であり、識別子ではありません。

## 10. インシデントと教訓のプロトコル

- インシデント（チャネル障害、ルール違反、ニアミス、覆された主張）は、日付・発生内容・処置とともに `ops/OPS-LOG.md` に追記します。覆された結論は成果物から削除し、ログに `OVERTURNED: …` とマークします。
- 行動を変える教訓は、*ルール*（本ファイル）またはブリーフテンプレートに書く必要があります——ログに書くだけでは不十分です。

## 11. セキュリティとプライバシー

- 認証情報をリポジトリに入れないこと。取得した素材にトークンが見つかった場合は、公開前に伏字化します。
- プライベートなインフラは、公開ドキュメントでは一般化して記述します。プローブのエビデンスは、プライベートなエンドポイントを含む場合はローカル限定に留めます。
- 美術館の画像：パブリックドメイン / オープンライセンスのソースのみ。帰属は `knowledge/INDEX.md` と画像マニフェストに記録します。

## 12. プロバイダー不安定期の作業方法（待复核）

モデルプロバイダーが不安定なとき（応答ストリームの途中終了、バッチ失敗など）、長時間の作業はこの方法に従います：

- **10〜15 分ごとにディスクへ書き込む**——小さな増分で。進捗をコンテキストの中だけに留めてはなりません。
- **まずプローブし、それから同じセッションを再開（resume）する**——ゼロ出力の実行は最初からやり直し、部分出力の実行は中断点から続行します。着地済みのものを確認せずに白紙から再開してはなりません。
- **実行中の各作業項目に 4 部構成の `RESUME.md` を維持する**——完了した手順 / 取得済み素材の一覧 + URL / 次の手順 / 検証済みの結論。ヘッダーに書き込みパスの契約を記載（テンプレート：`templates/resume.md`）。再開した担当者はまずこれを読み、すでに着地した素材を再取得しません。
- **完全性のためにラウンドを重ね、品質を犠牲にして完了を取らない**——並行性を維持し、基準を下げるのではなく新しいバッチで補います。
